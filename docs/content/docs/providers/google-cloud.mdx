## Using Google Cloud Storage

Google Cloud Storage serves an S3-compatible XML API at `https://storage.googleapis.com`. Pushduck talks to it with the generic `s3Compatible` provider and a GCS **HMAC key**: presigned uploads and downloads, multipart uploads and the Storage API all use the same requests they use against S3.

<Callout type="info">
  There is no `gcs` provider. Service-account JSON keys do not work with the S3 API — Google's interoperability layer authenticates with HMAC keys instead. See [Simple migration from Amazon S3](https://cloud.google.com/storage/docs/aws-simple-migration).
</Callout>

## 1. Create a Bucket

```bash
gcloud storage buckets create gs://my-app-uploads --location=us-central1
```

Or in the [Cloud Console](https://console.cloud.google.com/storage): **Create bucket**, pick a name and a location.

## 2. Create an HMAC Key

HMAC keys belong to a service account. Give the account access to the bucket, then create a key for it:

```bash
# A service account for uploads, with object access on this bucket only
gcloud iam service-accounts create pushduck-uploads
gcloud storage buckets add-iam-policy-binding gs://my-app-uploads \
  --member="serviceAccount:pushduck-uploads@YOUR_PROJECT.iam.gserviceaccount.com" \
  --role="roles/storage.objectAdmin"

# The HMAC key pushduck signs with
gcloud storage hmac create pushduck-uploads@YOUR_PROJECT.iam.gserviceaccount.com
```

The output contains an `accessId` (starts with `GOOG`) and a `secret`. The secret is shown once.

Or in the Console: **Cloud Storage → Settings → Interoperability → Create a key for a service account**.

## 3. Configure CORS

The browser uploads straight to GCS, so the bucket must allow your origin. Multipart uploads read each part's `ETag`, so it must be exposed:

```json title="cors.json"
[
  {
    "origin": ["http://localhost:3000", "https://yourdomain.com"],
    "method": ["GET", "PUT", "HEAD"],
    "responseHeader": ["Content-Type", "ETag"],
    "maxAgeSeconds": 3600
  }
]
```

```bash
gcloud storage buckets update gs://my-app-uploads --cors-file=cors.json
```

This is GCS's own CORS format, applied with `gcloud` — not the S3 `CORSRules` format.

## 4. Configure Your App

```bash title=".env.local"
GCS_HMAC_ACCESS_ID=GOOG...
GCS_HMAC_SECRET=...
GCS_BUCKET=my-app-uploads
```

```typescript title="lib/upload.ts"
import { createUploadConfig } from "pushduck/server";

export const { s3, storage } = createUploadConfig()
  .provider("s3Compatible", {
    endpoint: "https://storage.googleapis.com",
    bucket: process.env.GCS_BUCKET!,
    accessKeyId: process.env.GCS_HMAC_ACCESS_ID!,
    secretAccessKey: process.env.GCS_HMAC_SECRET!,
    region: "auto",
  })
  .build();
```

- `region: "auto"` is what Google's own S3 samples sign with.
- Requests are path-style (`storage.googleapis.com/<bucket>/<key>`), which GCS serves.
- Leave `acl` unset. Buckets with uniform bucket-level access (the default) reject per-object ACLs; control access with IAM instead.

## Reading Uploaded Files

Objects are private by default. Hand out short-lived signed URLs:

```typescript
const url = await storage.download.presignedUrl("avatars/me.png", 3600);
```

For public files, grant `allUsers` the **Storage Object Viewer** role on the bucket. Objects are then readable at `https://storage.googleapis.com/my-app-uploads/<key>`, or through a CDN you set as `customDomain`.

## Common Issues

**`403 SignatureDoesNotMatch`** → The HMAC secret is wrong, or a service-account JSON key was used instead of an HMAC key.

**`403 AccessDenied`** → The HMAC key's service account lacks a role on the bucket, or the key is inactive.

**`400 InvalidArgument` mentioning ACLs** → The bucket uses uniform bucket-level access; remove `acl` from the config.

**Browser request blocked by CORS** → Check the bucket's CORS rules include your origin and `PUT`, and expose `ETag` for multipart uploads.
