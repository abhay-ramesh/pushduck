## Using Google Cloud Storage

Google Cloud Storage serves an S3-compatible XML API at `https://storage.googleapis.com`. Pushduck uploads through it with an **HMAC key** — an access ID starting `GOOG` and a secret — so presigned uploads and downloads, multipart uploads and the Storage API all work the same way they do on S3.

<Callout type="info">
  Service-account JSON keys do not work here. The XML API's S3-style signatures need an HMAC key; Google's [Simple migration from Amazon S3](https://cloud.google.com/storage/docs/aws-simple-migration) describes the same setup.
</Callout>

Everything on this page was run against a real bucket: presigned `PUT` and `GET`, a three-part multipart upload, list, metadata and delete, and the router's presign → upload → complete flow behind a CORS preflight.

## 1. Create a Bucket

```bash
gcloud storage buckets create gs://my-app-uploads --location=us-central1
```

New buckets use **uniform bucket-level access**: permissions come from IAM, and per-object ACLs are rejected. Pushduck never sends ACLs to GCS, so this works as-is.

## 2. Create an HMAC Key

There are two kinds. Use whichever your organization allows.

### Service-account key (recommended)

Scoped to one service account, which you can limit to one bucket:

```bash
gcloud iam service-accounts create pushduck-uploads
gcloud storage buckets add-iam-policy-binding gs://my-app-uploads \
  --member="serviceAccount:pushduck-uploads@YOUR_PROJECT.iam.gserviceaccount.com" \
  --role="roles/storage.objectAdmin"
gcloud storage hmac create pushduck-uploads@YOUR_PROJECT.iam.gserviceaccount.com
```

The output has an `accessId` and a `secret`. The secret is shown once.

<Callout type="warn">
  Many organizations enforce the `iam.disableServiceAccountKeyCreation` policy, which blocks this command with `HTTPError 412: Request violates constraint`. Ask an Organization Policy Administrator for an exception on the project, or use a user-account key instead.
</Callout>

### User-account key

Created in the Console only: **Cloud Storage → Settings → [Interoperability](https://console.cloud.google.com/storage/settings;tab=interoperability) → Access keys for your user account → Create a key**. It carries all of your own Cloud Storage access, so prefer a service-account key where you can.

## 3. Configure CORS

The browser uploads straight to GCS, so the bucket must allow your origin. Multipart uploads read each part's `ETag`, so expose it:

```json title="cors.json"
[
  {
    "origin": ["http://localhost:3000", "https://yourdomain.com"],
    "method": ["GET", "PUT", "HEAD"],
    "responseHeader": ["Content-Type", "ETag"],
    "maxAgeSeconds": 3600
  }
]
```

```bash
gcloud storage buckets update gs://my-app-uploads --cors-file=cors.json
```

This is GCS's own CORS format, applied with `gcloud` — not the S3 `CORSRules` format.

## 4. Configure Your App

```bash title=".env.local"
GCS_ACCESS_KEY_ID=GOOG...
GCS_SECRET_ACCESS_KEY=...
GCS_BUCKET=my-app-uploads
```

```typescript title="lib/upload.ts"
import { createUploadConfig } from "pushduck/server";

export const { s3, storage } = createUploadConfig()
  .provider("gcs", {
    bucket: process.env.GCS_BUCKET!,
    accessKeyId: process.env.GCS_ACCESS_KEY_ID!,
    secretAccessKey: process.env.GCS_SECRET_ACCESS_KEY!,
  })
  .build();
```

| Option            | Required | Default                          | Description                                                                 |
| ----------------- | -------- | -------------------------------- | --------------------------------------------------------------------------- |
| `bucket`          | Yes      |                                  | The bucket name.                                                            |
| `accessKeyId`     | Yes      |                                  | HMAC access ID (`GOOG…`).                                                   |
| `secretAccessKey` | Yes      |                                  | HMAC secret.                                                                |
| `region`          | No       | `auto`                           | Signing region. `auto` works for every location; the bucket's own location also works. |
| `endpoint`        | No       | `https://storage.googleapis.com` | The XML API endpoint.                                                       |
| `forcePathStyle`  | No       | `true`                           | `false` addresses the bucket as `my-app-uploads.storage.googleapis.com`.    |
| `customDomain`    | No       |                                  | A CDN or load balancer in front of a public bucket, used for public URLs.   |

`acl` is accepted and ignored: GCS controls access with IAM, and uniform-access buckets reject per-object ACLs.

## Reading Uploaded Files

Objects are private by default. Hand out short-lived signed URLs:

```typescript
const url = await storage.download.presignedUrl("avatars/me.png", 3600);
```

For public files, grant `allUsers` the **Storage Object Viewer** role on the bucket. Objects are then readable at `https://storage.googleapis.com/my-app-uploads/<key>`, or through a CDN set as `customDomain`.

## Common Issues

**`Google Cloud Storage needs an HMAC key … not a service-account key`** → The config passes `projectId` or `keyFilename`. Replace them with `accessKeyId` and `secretAccessKey` from an HMAC key.

**`HTTPError 412: Request violates constraint 'constraints/iam.disableServiceAccountKeyCreation'`** → Your organization blocks service-account keys. See [Create an HMAC Key](#2-create-an-hmac-key).

**`403 SignatureDoesNotMatch`** → The HMAC secret is wrong, or the key was deactivated.

**`403 AccessDenied`** → The key's account has no role on the bucket.

**Browser request blocked by CORS** → Check the bucket's CORS rules include your origin and `PUT`, and expose `ETag` for multipart uploads.
