## CORS Configuration

Browsers upload straight to your bucket with a presigned URL, so the **bucket** — not your app — decides whether the upload is allowed. Before the `PUT`, the browser sends a preflight `OPTIONS` request from your page's origin (e.g. `http://localhost:3000`) to the bucket. If no CORS rule allows that origin, the upload fails with a bare network error, and nothing reaches your server.

### Check and fix it with the CLI

```bash
# Will browser uploads from these origins work?
npx @pushduck/cli@latest cors check --origin http://localhost:3000 https://app.example.com

# Add the ones that don't, keeping the bucket's other rules
npx @pushduck/cli@latest cors apply --origin http://localhost:3000 https://app.example.com
```

`cors check` reads the bucket's rules, sends the same preflight a browser would, and reports per origin whether uploads, downloads and reading `ETag` work. It exits non-zero when any origin would fail, so it can run in CI. `cors apply` shows the change as a diff and asks before writing. Both use the credentials `pushduck test` uses, from the environment, `.env.local` or `.env`. See the [CLI reference](/docs/api/cli#cors---check-and-fix-bucket-cors) for details.

Each new origin needs a rule: a dev server on another port, a preview deployment, a custom domain. The usual sign of a missing rule is an app that works on `localhost:3000` and fails on a worktree's random port or in production. Use `cors apply` to add the origin rather than proxying uploads through your server or pinning the dev port.

### The rule pushduck needs

```json
{
  "CORSRules": [
    {
      "ID": "pushduck",
      "AllowedOrigins": ["http://localhost:3000", "https://app.example.com"],
      "AllowedMethods": ["PUT", "GET"],
      "AllowedHeaders": ["content-type", "x-amz-acl"],
      "ExposeHeaders": ["ETag"],
      "MaxAgeSeconds": 3600
    }
  ]
}
```

This is exactly what the browser client sends:

- **`PUT`** uploads a file, or one part of a multipart upload, to its presigned URL. **`GET`** downloads with `fetch`. Multipart create, complete and abort, deletes and `HEAD` checks all run on your server, so `POST`, `DELETE` and `HEAD` are not needed.
- **`content-type`** is sent on every upload. **`x-amz-acl`** is sent only on providers that accept ACLs (AWS S3, DigitalOcean Spaces, S3-compatible), because the server signs it into the URL. Leave it out on R2, MinIO, GCS and Neon.
- **`ETag`** must be exposed: the multipart uploader reads each part's ETag to complete the upload. A rule without it lets small files through and fails every large one.

Rules are matched in order, and only the **first** rule that matches an origin and method applies, including its `ExposeHeaders`. A later rule that exposes `ETag` does not help when an earlier one matches first. That is why `cors apply` puts pushduck's rule first.

An origin is `scheme://host[:port]` with no path and no trailing slash. One `*` is allowed (`https://*.example.com`). On R2, a port cannot be a wildcard, so list each port.

### Setting it by hand

`cors apply` does the following for you; these are the manual steps.

#### AWS S3

Save the JSON above as `cors-config.json`, then:

```bash
aws s3api put-bucket-cors --bucket your-bucket --cors-configuration file://cors-config.json
```

`put-bucket-cors` replaces the whole configuration, so include any rules you already have (`aws s3api get-bucket-cors --bucket your-bucket`). In the console, go to S3, then the bucket, then Permissions, then Cross-origin resource sharing (CORS). The console takes the bare array, without `CORSRules`.

#### Cloudflare R2

R2 implements `GetBucketCors` and `PutBucketCors` on its S3 API ([S3 API compatibility](https://developers.cloudflare.com/r2/api/s3/api/)). Changing bucket configuration requires an API token with **Admin Read & Write** permission. The **Object Read & Write** token your app uploads with can't do it ([R2 API tokens](https://developers.cloudflare.com/r2/api/tokens/)). Run `cors apply` with an admin token, or set the rule in the dashboard (R2, then the bucket, then Settings, then CORS Policy) or with `wrangler r2 bucket cors set`. Changes can take up to 30 seconds to apply ([R2 CORS](https://developers.cloudflare.com/r2/buckets/cors/)).

#### DigitalOcean Spaces

Spaces takes `PutBucketCors`, so `cors apply` works. By hand, use the Spaces settings in the control panel, `s3cmd setcors`, or the AWS CLI command above with `--endpoint-url https://<region>.digitaloceanspaces.com`.

#### Google Cloud Storage

GCS keeps CORS in its own JSON format, set with `gcloud` rather than the S3 API. `cors apply` prints the JSON and the command instead of applying them:

```json
[
  {
    "origin": ["http://localhost:3000", "https://app.example.com"],
    "method": ["PUT", "GET"],
    "responseHeader": ["content-type", "ETag"],
    "maxAgeSeconds": 3600
  }
]
```

```bash
gcloud storage buckets update gs://your-bucket --cors-file=cors.json
```

GCS uses `responseHeader` both for the headers a request may send and for the headers the page may read, so it lists both. The command replaces the bucket's configuration. Check the current one with `gcloud storage buckets describe gs://your-bucket --format="default(cors_config)"`. See [Configure CORS](https://cloud.google.com/storage/docs/using-cors).

#### MinIO (self-hosted)

Open-source MinIO has no per-bucket CORS. It answers `PutBucketCors` with `501 NotImplemented`, and its `GetBucketCors` result does not reflect what it allows. CORS is one server-wide setting that allows every origin by default and exposes `ETag`. To restrict it to your origins:

```bash
MINIO_API_CORS_ALLOW_ORIGIN="http://localhost:3000,https://app.example.com" minio server /data
# or, on a running server
mc admin config set myminio api cors_allow_origin="http://localhost:3000,https://app.example.com"
```

`cors check` works against MinIO, because it relies on the preflight. `cors apply` prints these commands.

#### Neon Object Storage

Neon supports `GetBucketCors` and `PutBucketCors`, so `cors apply` works. By hand, use the AWS CLI command above with `--endpoint-url "$AWS_ENDPOINT_URL_S3"`.

Neon does not support ACLs. Set a bucket's access level (`private` or `public_read`) when you create it; pushduck never sends `x-amz-acl` to Neon. See [Neon Object Storage](/docs/providers/neon-object-storage#4-configure-cors).

### Testing by hand

`cors check` sends this preflight for you. To see the raw answer:

```bash
curl -i -X OPTIONS \
  -H "Origin: http://localhost:3000" \
  -H "Access-Control-Request-Method: PUT" \
  -H "Access-Control-Request-Headers: content-type" \
  https://your-bucket.s3.us-east-1.amazonaws.com/any-key
```

An allowed origin gets a 2xx response with `Access-Control-Allow-Origin` set to that origin, and `PUT` and `content-type` in the allow lists. In the browser, a CORS failure shows up as a failed `OPTIONS` request in the Network tab.

## Understanding ACLs

Access Control Lists (ACLs) define who can access your uploaded files and what permissions they have. **Important: ACL implementation varies significantly across providers.**

### What are ACLs?

ACLs are permission sets that determine:
- **Who** can access files (users, groups, public)
- **What** they can do (read, write, delete)
- **How** permissions are inherited

### Common ACL Types

#### Public Access Levels

- **`public-read`**: Anyone can download the file
- **`public-read-write`**: Anyone can download and upload
- **`private`**: Only bucket owner has access
- **`authenticated-read`**: Only authenticated users can read

#### AWS S3 ACL Examples

```typescript
// Using PushDuck with S3 ACLs
const uploadConfig = createUploadConfig({
  provider: s3({
    bucket: "my-bucket",
    region: "us-east-1",
    acl: "public-read" // File will be publicly accessible
  }),
  // ... other config
});
```

### Provider-Specific ACL Differences

| Provider | Sends `acl`? | Make files public with |
| --- | --- | --- |
| AWS S3, DigitalOcean Spaces, S3-compatible | Yes | `acl`, or a bucket policy |
| Cloudflare R2 | No | Bucket public access (custom domain or r2.dev) |
| MinIO | No | A bucket policy (`mc anonymous set download`) |
| Neon Object Storage | No | Create the bucket as `public_read` |
| Google Cloud Storage | No | IAM on the bucket (`allUsers` → Storage Object Viewer) |

On providers marked "No", pushduck never sends `x-amz-acl` (they reject it) and
logs a warning when `acl` is set, either as a provider option or in
`.defaults()`. Objects get the bucket's access settings. Set `customDomain` to
the bucket's public URL so `file.url` points at it.

#### AWS S3
- **Full ACL Support**: Comprehensive ACL system
- **Canned ACLs**: Predefined permission sets
- **Custom ACLs**: Granular user/group permissions
- **Bucket Policies**: Override ACL settings

```typescript
// S3 supports traditional ACLs
const s3Config = s3({
  bucket: "my-bucket",
  acl: "public-read", // ✅ Supported
  // Custom ACL with specific permissions
  customAcl: {
    Owner: { ID: "owner-id", DisplayName: "Owner" },
    Grants: [
      {
        Grantee: { Type: "Group", URI: "http://acs.amazonaws.com/groups/global/AllUsers" },
        Permission: "READ"
      }
    ]
  }
});
```

#### Cloudflare R2
- **Limited ACL Support**: Basic public/private only
- **No Canned ACLs**: Doesn't support AWS-style ACL names
- **Bucket-Level Permissions**: Access controlled at bucket level

```typescript
// R2 has limited ACL support
const r2Config = cloudflareR2({
  bucket: "my-bucket",
  // ❌ acl: "public-read" // Not supported
  // Access controlled via Cloudflare dashboard or API
});
```

#### DigitalOcean Spaces
- **S3-Compatible ACLs**: Supports most S3 ACL types
- **Public/Private Toggle**: Simple public access control
- **CDN Integration**: Automatic CDN for public files

```typescript
// Spaces supports basic S3 ACLs
const spacesConfig = digitalOceanSpaces({
  bucket: "my-space",
  acl: "public-read", // ✅ Supported
  region: "nyc3"
});
```

#### MinIO (Self-Hosted)
- **Policy-Based**: Uses bucket policies instead of ACLs
- **No Traditional ACLs**: Custom permission system
- **IAM Integration**: Role-based access control

```typescript
// MinIO uses policies, not ACLs
const minioConfig = minio({
  endpoint: "https://minio.yourdomain.com",
  bucket: "my-bucket",
  // ❌ acl: "public-read" // Not supported
  // Access controlled via MinIO policies
});
```

### ACL Best Practices

#### Security Considerations

1. **Default to Private**: Start with `private` ACL
2. **Explicit Public Access**: Only make files public when necessary
3. **Regular Audits**: Review public files periodically
4. **Bucket Policies**: Use bucket policies for complex permissions

#### Implementation Strategy

```typescript
// Environment-based ACL configuration
const getAcl = () => {
  if (process.env.NODE_ENV === 'development') {
    return 'public-read'; // Easy testing
  }
  
  if (process.env.FILE_TYPE === 'profile-images') {
    return 'public-read'; // Profile images need public access
  }
  
  return 'private'; // Default to private
};

const uploadConfig = createUploadConfig({
  provider: s3({
    bucket: process.env.S3_BUCKET!,
    acl: getAcl()
  })
});
```

## Provider-Specific Considerations

### AWS S3
- **Bucket Policies Override ACLs**: Bucket policies take precedence
- **Block Public Access**: May prevent ACL-based public access
- **IAM Permissions**: Required for ACL operations

### Cloudflare R2
- **Dashboard Configuration**: Set public access via Cloudflare dashboard
- **Custom Domains**: Use custom domains for public files
- **Workers Integration**: Use Cloudflare Workers for access control

### DigitalOcean Spaces
- **CDN Integration**: Automatic CDN for public files
- **Subdomain Access**: Public files accessible via subdomain
- **CORS + ACL**: Both required for browser uploads

### MinIO
- **Policy-Only**: No ACL support, use bucket policies
- **Admin Configuration**: Set policies via MinIO admin
- **Custom Authentication**: Integrate with your auth system

## Common Issues & Troubleshooting

### CORS Issues

#### Symptom: "CORS policy" errors in browser console

Run `npx @pushduck/cli@latest cors check --origin <the page's origin>`. It names what is missing (the origin, `PUT`, or a header), and `cors apply` with the same origins fixes it.

#### Symptom: Uploads work locally but fail in production, or on another port

The bucket allows `localhost:3000` but not the other origin. Add it with `cors apply --origin https://app.example.com`. Each port and each preview domain is a separate origin.

#### Symptom: Small files upload, large ones fail with a missing ETag

The rule that serves your origin does not expose `ETag`, which multipart uploads read. `cors check` reports this as "ETag readable after upload", and `cors apply` fixes it.

### ACL Issues

#### Symptom: Files uploaded but not accessible

**Solution:**
1. Check if bucket has "Block Public Access" enabled
2. Verify ACL permissions match requirements
3. Review bucket policies for conflicts

#### Symptom: ACL settings ignored

**Solution:**
1. Provider may not support ACLs (R2, MinIO)
2. Bucket policies may override ACL settings
3. Check IAM permissions for ACL operations

### Mixed Issues

#### Symptom: Uploads succeed but files have wrong permissions

**Solution:**
```typescript
// Ensure ACL is set correctly for your provider
const config = createUploadConfig({
  provider: s3({
    bucket: "my-bucket",
    acl: "public-read", // Only for S3-compatible providers
  }),
  onUploadComplete: async ({ file, url }) => {
    // Verify file accessibility
    const response = await fetch(url, { method: 'HEAD' });
    if (!response.ok) {
      console.error('File not publicly accessible:', response.status);
    }
  }
});
```

### Debug Checklist

- [ ] `pushduck cors check` passes for every origin the app is served from
- [ ] ACL settings match provider capabilities
- [ ] Bucket policies don't conflict with ACLs
- [ ] IAM permissions allow required operations
- [ ] Block Public Access settings reviewed
- [ ] CDN/proxy configurations considered
