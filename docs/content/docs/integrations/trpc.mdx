## Using pushduck with tRPC

tRPC enables end-to-end typesafe APIs with excellent TypeScript integration. With pushduck, you use **tRPC for storage operations** (listing, deleting, metadata) while **file uploads happen through your framework's routes** using pushduck handlers. This gives you the best of both worlds: framework-native uploads with type-safe storage management.

<Callout type="info">
  **Separation of Concerns**: File uploads use your framework's native upload routes with pushduck handlers, while tRPC procedures handle all storage-related CRUD operations using pushduck's storage API for full type safety.
</Callout>

    ```typescript title="server/trpc.ts"
    import { initTRPC, TRPCError } from '@trpc/server';
    import { z } from 'zod';
    import { storage } from '~/lib/storage';

    const t = initTRPC.create();

    export const appRouter = t.router({
      files: t.router({
        // List files with pagination
        list: t.procedure
          .input(z.object({ 
            prefix: z.string().optional(),
            limit: z.number().min(1).max(100).default(20),
            cursor: z.string().optional()
          }))
          .query(async ({ input }) => {
            const result = await storage.list.paginated({
              prefix: input.prefix,
              maxKeys: input.limit,
              continuationToken: input.cursor,
            });
            
            return {
              files: result.files,
              nextCursor: result.nextContinuationToken,
              hasMore: result.isTruncated,
            };
          }),

        // Get file metadata
        getInfo: t.procedure
          .input(z.object({ key: z.string() }))
          .query(async ({ input }) => {
            const info = await storage.metadata.getInfo(input.key);
            if (!info.exists) {
              throw new TRPCError({ 
                code: 'NOT_FOUND', 
                message: 'File not found' 
              });
            }
            return info;
          }),

        // Get multiple files info
        getBatch: t.procedure
          .input(z.object({ keys: z.array(z.string()) }))
          .query(async ({ input }) => {
            return await storage.metadata.getBatch(input.keys);
          }),

        // Delete file
        delete: t.procedure
          .input(z.object({ key: z.string() }))
          .mutation(async ({ input }) => {
            const result = await storage.delete.file(input.key);
            return { success: result.success };
          }),

        // Delete multiple files
        deleteBatch: t.procedure
          .input(z.object({ keys: z.array(z.string()) }))
          .mutation(async ({ input }) => {
            const result = await storage.delete.files(input.keys);
            return { 
              success: result.success,
              deleted: result.deleted,
              errors: result.errors,
            };
          }),

        // Generate download URL
        getDownloadUrl: t.procedure
          .input(z.object({ 
            key: z.string(),
            expiresIn: z.number().optional()
          }))
          .query(async ({ input }) => {
            const result = await storage.download.presignedUrl(
              input.key, 
              input.expiresIn
            );
            return { url: result.url, expiresAt: result.expiresAt };
          }),

        // Search files by extension
        searchByExtension: t.procedure
          .input(z.object({ 
            extension: z.string(),
            prefix: z.string().optional()
          }))
          .query(async ({ input }) => {
            return await storage.list.byExtension(
              input.extension, 
              input.prefix
            );
          }),

        // Search files by size range
        searchBySize: t.procedure
          .input(z.object({
            minSize: z.number().optional(),
            maxSize: z.number().optional(),
            prefix: z.string().optional()
          }))
          .query(async ({ input }) => {
            return await storage.list.bySize(
              input.minSize,
              input.maxSize,
              input.prefix
            );
          }),

        // Get storage statistics
        getStats: t.procedure
          .input(z.object({ prefix: z.string().optional() }))
          .query(async ({ input }) => {
            const files = await storage.list.files({ prefix: input.prefix });
            
            const stats = files.files.reduce((acc, file) => {
              acc.totalSize += file.size;
              acc.count += 1;
              
              const ext = file.key.split('.').pop()?.toLowerCase() || 'unknown';
              acc.byExtension[ext] = (acc.byExtension[ext] || 0) + 1;
              
              return acc;
            }, {
              totalSize: 0,
              count: 0,
              byExtension: {} as Record<string, number>
            });
            
            return stats;
          }),
      }),
    });

    export type AppRouter = typeof appRouter;
    ```

## Client-Side Usage

Uploads bypass tRPC entirely — bytes go straight to storage via presigned URLs —
while tRPC owns everything *around* them: listing, deleting, metadata, and
permissions. On the client that means the pushduck hook sits alongside your
tRPC hooks, and the two are joined by React Query cache invalidation.

### Upload Component with Cache Invalidation

The key integration point: when an upload completes, invalidate the tRPC queries
that list files, so your UI updates the same way it would after any mutation.

```tsx title="src/components/FileUpload.tsx"
import { useUploadRoute } from "pushduck/client";
import { trpc } from "~/utils/trpc";
import type { AppUploadRouter } from "~/lib/upload";

export function FileUpload() {
  const utils = trpc.useUtils();

  const { files, progress, isUploading, uploadFiles, cancel } =
    useUploadRoute<AppUploadRouter>("imageUpload", {
      endpoint: "/api/upload",
      onSuccess: async () => {
        // Same invalidation you would run after a tRPC mutation — the upload
        // just happened over a different transport.
        await utils.files.list.invalidate();
        await utils.files.getStats.invalidate();
      },
      onError: (error) => console.error("Upload failed:", error),
    });

  return (
    <div className="space-y-4">
      <input
        type="file"
        multiple
        accept="image/*"
        disabled={isUploading}
        onChange={(e) => uploadFiles(Array.from(e.target.files ?? []))}
      />

      {isUploading && <progress value={progress} max={100} />}

      {files.map((file) => (
        <div key={file.id} className="flex gap-2 items-center">
          <span>{file.name}</span>
          <span>
            {file.status} ({file.progress}%)
          </span>
          {file.status === "uploading" && (
            <button onClick={() => cancel(file.id)}>Cancel</button>
          )}
        </div>
      ))}
    </div>
  );
}
```

### Uploads as a Mutation

The component above lets the pushduck hook own loading and error state. If you
would rather tRPC and TanStack Query own it — so uploads sit in the same
`isPending` / `onError` / retry machinery as the rest of your app — use the
promise-based `uploadFiles` instead of the hook:

```tsx title="src/components/UploadMutation.tsx"
import { uploadFiles } from "pushduck/client";
import { useMutation } from "@tanstack/react-query";
import { trpc } from "~/utils/trpc";

export function UploadMutation() {
  const utils = trpc.useUtils();

  const { mutate: upload, isPending, error } = useMutation({
    mutationFn: (files: File[]) =>
      uploadFiles({
        files,
        route: "imageUpload",
        endpoint: "/api/upload",
        onFileStateChange: (file) => {
          // Per-file progress, if you want to render it.
          console.log(file.name, file.status, file.progress);
        },
      }),
    onSuccess: async ({ files, failedFiles }) => {
      if (failedFiles.length > 0) {
        console.warn(`${failedFiles.length} file(s) failed`);
      }
      await utils.files.list.invalidate();
    },
  });

  return (
    <>
      <input
        type="file"
        multiple
        disabled={isPending}
        onChange={(e) => upload(Array.from(e.target.files ?? []))}
      />
      {error && <p role="alert">{error.message}</p>}
    </>
  );
}
```

<Callout type="info">
  **Which one should I use?**

  - **`useUploadRoute`** — the hook owns per-file state, progress, speed, ETA,
    and cancellation. Fewest moving parts for an upload-centric UI.
  - **`uploadFiles` + `useMutation`** — your async-state library owns loading
    and errors, so uploads inherit your existing retry, error-boundary, and
    devtools setup. Track per-file progress yourself via `onFileStateChange`.

  Both drive the same engine, so behaviour is identical.
</Callout>

#### Resolve vs. reject

`uploadFiles` distinguishes two kinds of failure, which is what makes it behave
correctly under `useMutation`:

| Outcome | Result |
| --- | --- |
| Batch could not run — auth rejected, route missing, network down | **Rejects** with `UploadBatchError`, so `onError` fires and retries apply |
| Some files failed, others succeeded | **Resolves** with `{ files, failedFiles }` |

Partial failure resolves deliberately: those bytes are already in storage, and
throwing would discard the successful uploads along with the failed ones.


### Upload and Manage Together

A file browser that uploads through pushduck and manages through tRPC:

```tsx title="src/components/FileManager.tsx"
import { useUploadRoute } from "pushduck/client";
import { trpc } from "~/utils/trpc";

export function FileManager() {
  const utils = trpc.useUtils();

  const { data: files, isLoading } = trpc.files.list.useQuery({});

  const deleteFile = trpc.files.delete.useMutation({
    onSuccess: () => utils.files.list.invalidate(),
  });

  const { uploadFiles, isUploading, progress } = useUploadRoute("imageUpload", {
    endpoint: "/api/upload",
    onSuccess: () => utils.files.list.invalidate(),
  });

  if (isLoading) return <p>Loading…</p>;

  return (
    <div>
      <input
        type="file"
        multiple
        disabled={isUploading}
        onChange={(e) => uploadFiles(Array.from(e.target.files ?? []))}
      />
      {isUploading && <progress value={progress} max={100} />}

      <ul>
        {files?.map((file) => (
          <li key={file.key}>
            {file.key}
            <button
              onClick={() => deleteFile.mutate({ key: file.key })}
              disabled={deleteFile.isPending}
            >
              Delete
            </button>
          </li>
        ))}
      </ul>
    </div>
  );
}
```

<Callout type="info">
  **Two routers, by design.** You export `AppRouter` (tRPC) and
  `AppUploadRouter` (pushduck) separately. tRPC is JSON-RPC and cannot carry
  binary bodies or report upload progress, so routing files through it would
  mean base64-encoding them and losing progress, cancellation, and direct-to-S3
  transfer. The two systems stay parallel and meet at the cache.
</Callout>

### Optimistic UI

Because `files` from the hook already carries per-file status and progress, you
usually do not need optimistic updates for the upload itself — render the hook's
state during the upload and the invalidated tRPC query afterwards.


## Authentication Integration

This is where the two systems most need to agree. tRPC derives the user in
`createContext`; pushduck's middleware receives the raw `Request`. Write the
resolver **once** and call it from both — otherwise your auth rules drift apart.

### One Resolver, Two Consumers

```typescript title="src/server/auth.ts"
/**
 * Single source of truth for "who is making this request".
 * Consumed by tRPC's context and by pushduck's upload middleware.
 */
export async function getUserFromRequest(req: Request) {
  const authHeader = req.headers.get("authorization");
  if (!authHeader?.startsWith("Bearer ")) return null;

  try {
    return await validateToken(authHeader.substring(7));
  } catch {
    return null;
  }
}
```

```typescript title="src/server/trpc.ts"
import { initTRPC, TRPCError } from "@trpc/server";
import { getUserFromRequest } from "./auth";

export const createContext = async ({ req }: { req: Request }) => ({
  user: await getUserFromRequest(req),
});

type Context = Awaited<ReturnType<typeof createContext>>;
const t = initTRPC.context<Context>().create();

const isAuthenticated = t.middleware(({ next, ctx }) => {
  if (!ctx.user) throw new TRPCError({ code: "UNAUTHORIZED" });
  return next({ ctx: { ...ctx, user: ctx.user } });
});

export const protectedProcedure = t.procedure.use(isAuthenticated);
export const router = t.router;
```

```typescript title="src/lib/upload.ts"
import { getUserFromRequest } from "~/server/auth";

const uploadRouter = s3.createRouter({
  imageUpload: s3
    .image()
    .maxFileSize("5MB")
    // The same resolver tRPC uses — one place to change auth rules.
    .middleware(async ({ req }) => {
      const user = await getUserFromRequest(req);
      if (!user) throw new Error("Unauthorized");

      return {
        userId: user.id,
        // Never trust client-provided identity claims; derive them here.
        role: user.role,
      };
    })
    .paths({
      // Scope uploads to the same prefix your tRPC procedures enforce.
      prefix: ({ metadata }) => `users/${metadata.userId}`,
    }),
});

export type AppUploadRouter = typeof uploadRouter;
export const { GET, POST } = uploadRouter.handlers;
```

<Callout type="warn">
  Keep the **path prefix** and your tRPC procedures' ownership checks in sync.
  If uploads land in `users/{id}/` then `files.list` and `files.delete` must
  scope to that same prefix, or a user will be able to read or delete another
  user's objects.
</Callout>

### Reusing tRPC Procedures in `onUploadComplete`

When an upload finishes you usually want to write a database row — logic that
probably already exists as a tRPC procedure. Use `createCaller` to invoke it
server-side instead of duplicating it:

```typescript title="src/lib/upload.ts"
import { appRouter } from "~/server/routers/_app";

const uploadRouter = s3.createRouter({
  imageUpload: s3
    .image()
    .middleware(async ({ req }) => {
      const user = await getUserFromRequest(req);
      if (!user) throw new Error("Unauthorized");
      return { userId: user.id, user };
    })
    .onUploadComplete(async ({ file, metadata }) => {
      // Same procedure your client calls — one implementation, one set of
      // validation rules, called with an authenticated context.
      const caller = appRouter.createCaller({ user: metadata.user });

      await caller.files.record({
        key: file.key,
        name: file.name,
        size: file.size,
        contentType: file.type,
      });
    }),
});
```

<Callout type="info">
  `createCaller` is tRPC's server-side invocation API. It runs the procedure's
  input validation and middleware exactly as an HTTP call would, so business
  rules cannot drift between the upload path and the API path.
</Callout>

### Scoped Storage Procedures

```typescript title="src/server/routers/files.ts"
import { z } from "zod";
import { TRPCError } from "@trpc/server";
import { storage } from "~/lib/storage";
import { protectedProcedure, router } from "../trpc";

export const filesRouter = router({
  list: protectedProcedure
    .input(z.object({ prefix: z.string().optional() }))
    .query(async ({ input, ctx }) => {
      // Same prefix convention the upload router writes to.
      const userPrefix = `users/${ctx.user.id}/${input.prefix ?? ""}`;
      return storage.list.files({ prefix: userPrefix });
    }),

  delete: protectedProcedure
    .input(z.object({ key: z.string() }))
    .mutation(async ({ input, ctx }) => {
      if (!input.key.startsWith(`users/${ctx.user.id}/`)) {
        throw new TRPCError({ code: "FORBIDDEN" });
      }
      return storage.delete.file(input.key);
    }),

  record: protectedProcedure
    .input(
      z.object({
        key: z.string(),
        name: z.string(),
        size: z.number(),
        contentType: z.string(),
      })
    )
    .mutation(async ({ input, ctx }) => {
      return db.file.create({ data: { ...input, userId: ctx.user.id } });
    }),
});
```


## Real-time Updates with Subscriptions

```typescript title="server/trpc.ts"
import { observable } from '@trpc/server/observable';
import { EventEmitter } from 'events';

const fileEventEmitter = new EventEmitter();

export const appRouter = t.router({
  files: t.router({
    // ... other procedures

    // Real-time file updates
    onUpdate: protectedProcedure
      .subscription(({ ctx }) => {
        return observable<{ type: 'uploaded' | 'deleted'; file: any }>((emit) => {
          const onFileEvent = (data: any) => {
            // Only emit events for this user's files
            if (data.userId === ctx.user.id) {
              emit.next(data);
            }
          };
          
          fileEventEmitter.on('file:event', onFileEvent);
          
          return () => {
            fileEventEmitter.off('file:event', onFileEvent);
          };
        });
      }),
  }),
});

// Emit events from upload completion
export const emitFileEvent = (type: 'uploaded' | 'deleted', file: any, userId: string) => {
  fileEventEmitter.emit('file:event', { type, file, userId });
};
```

## Key Advantages

### **Clear Separation**
- **Uploads**: Framework-native routes with pushduck handlers
- **Storage Operations**: Type-safe tRPC procedures with pushduck storage API
- **Client**: Framework upload hooks + tRPC queries/mutations

### **Best of Both Worlds**
- **Framework-optimized uploads** (progress, validation, middleware)
- **Type-safe storage management** (list, delete, search, metadata)
- **Unified developer experience** with consistent patterns

### **Scalable Architecture**
- **Independent scaling** of upload and API operations
- **Flexible deployment** (separate services if needed)
- **Framework agnostic** storage operations

## Troubleshooting

<Callout type="warn">
  **Common Issues**
  
  1. **Mixed responsibilities**: Don't try to handle uploads in tRPC procedures - use framework routes
  2. **Type mismatches**: Ensure storage operations use the same config as upload routes
  3. **Authentication**: Sync auth between upload middleware and tRPC context
  4. **CORS**: Configure CORS for both `/api/trpc` and `/api/upload` endpoints
</Callout>
